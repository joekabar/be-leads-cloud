# Data Model

## Why append-only provenance?

Every scraped fact is stored as a new row in `observations` — never an UPDATE to an existing row.
This design gives us:

- **Full audit history**: every value observed for every field is permanently recorded with its source, timestamp, and confidence.
- **Multi-source reconciliation**: two sources can disagree on a company's phone number; both observations are kept and the winner is computed by confidence + recency, not last-write-wins.
- **JSONB flexibility**: different field types (phone, address, financials) have different shapes; JSONB avoids a schema migration per new field variant.
- **Conflict-free merging**: because we only INSERT, parallel scrapers never conflict with each other.

The rule is enforced at multiple levels: `ObservationsRepo` has no `update` or `delete` methods, a pre-commit script (`verify_no_updates.sh`) blocks SQL UPDATE on the protected tables, and tests assert that the methods don't exist.

## The four tables

### `schema_version`
Tracks which migration files have been applied. Managed exclusively by `src/scraper/db/migrations/runner.py`.

### `run_log`
One row per pipeline run. Every `observations` row has a `run_id` FK → `run_log`. This ties each scraped value to the exact pipeline run that produced it.

| column      | type        | notes                                  |
|-------------|-------------|----------------------------------------|
| run_id      | UUID PK     | generated by `RunsRepo.start_run()`    |
| started_at  | TIMESTAMPTZ |                                        |
| ended_at    | TIMESTAMPTZ | NULL while running                     |
| source      | TEXT        | which source module ran                |
| sector_slug | TEXT        | optional filter used for the run       |
| city_slug   | TEXT        | optional filter used for the run       |
| jobs_done   | INTEGER     | filled in by `RunsRepo.finish_run()`   |
| jobs_failed | INTEGER     |                                        |

### `observations` — append-only fact store
Every scraped field value is one row. `UPDATE` is forbidden; new values become new rows.

| column      | type        | notes                                                              |
|-------------|-------------|--------------------------------------------------------------------|
| id          | BIGSERIAL PK|                                                                    |
| kbo_number  | CHAR(10)    | Belgian enterprise number (10 digits, stdnum-compacted)            |
| field       | TEXT        | one of the allowed field names (see §fields below)                 |
| value       | JSONB       | field-specific shape (see provenance-schema skill §7)              |
| raw_value   | TEXT        | original unparsed string from the source, for debugging            |
| source      | TEXT        | one of the allowed source names                                    |
| source_url  | TEXT        | URL or file path of the raw artefact                               |
| observed_at | TIMESTAMPTZ | when the scraper fetched this fact                                 |
| confidence  | NUMERIC(3,2)| 0.00–1.00, prior from source table × recency decay × consensus     |
| run_id      | UUID        | FK → run_log(run_id) ON DELETE RESTRICT                            |

### `jobs` — worker queue
Standard `SELECT … FOR UPDATE SKIP LOCKED` queue. Workers call `JobsRepo.pop_pending()` which atomically claims one job without blocking other workers.

| column        | type        | notes                                          |
|---------------|-------------|------------------------------------------------|
| id            | BIGSERIAL PK|                                                |
| type          | TEXT        | job kind, e.g. "fetch_company"                 |
| payload       | JSONB       | job-specific parameters                        |
| status        | TEXT        | pending / running / done / failed / dead       |
| priority      | INTEGER     | higher = claimed first (default 5)             |
| next_retry_at | TIMESTAMPTZ | workers skip jobs whose retry time is future   |
| last_error    | TEXT        | set by `mark_failed` / `mark_dead`             |
| parent_job_id | BIGINT      | optional FK to parent job (self-reference)     |

A partial unique index (`uniq_jobs_active_dedup`) prevents double-enqueueing when `payload` contains a `dedup_key`.

## Materialised view: `companies_current`

```sql
SELECT DISTINCT ON (kbo_number, field)
       kbo_number, field, value, source, observed_at, confidence
FROM observations
ORDER BY kbo_number, field, confidence DESC, observed_at DESC;
```

Returns the single highest-confidence (then newest) observation per `(kbo_number, field)`.
Refreshed via `REFRESH MATERIALIZED VIEW CONCURRENTLY companies_current` after each pipeline run.
Concurrent refresh requires the unique index `uniq_companies_current (kbo_number, field)`.

**Never refresh from a repository method.** Refresh belongs in `src/scraper/pipeline/consolidate.py` (added in a later prompt).

## The no-UPDATE rule

`UPDATE observations …` and `UPDATE companies_current …` are permanently forbidden.

Enforcement layers:
1. `ObservationsRepo` has no `update` or `delete` methods (tests assert this).
2. `.claude/skills/provenance-schema/scripts/verify_no_updates.sh` — pre-commit grep guard (exits 2 if found).
3. `tests/integration/db/test_no_updates_guard.py` — asserts the guard script works correctly.

## What is a "field"?

Allowed static fields (defined in `src/scraper/db/fields.py`):
`phone | email | website | address | name | founding_date | nace_code | function_holder | activity_summary | website_age | postal_code | status`

Financial fields follow the pattern `{revenue|profit|employees}_{YYYY}` with a four-digit year.
New fields must be added to `ALLOWED_FIELDS` (or the regex in `is_financial_field`) before any source can write them.

See `.claude/skills/provenance-schema/SKILL.md` for full details including confidence priors, JSONB shapes, and source taxonomy.
